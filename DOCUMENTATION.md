Challenges that occured (currently in reversed order):

In order to assess whether moves are legal, it is necessary to do integer calculation on initial and final positions. Specifically, the change in x and y for the piece. It is also necessary to check the board is clear in between the path. Initially, the plan was to implement the checks in GameManager.cc right before a move command is executed. However, since coordinates are initially passed as a 2 character string, it is difficult to directly do math on it. Converting it would risk duplicate code already written in ChessBoard.cc. There is the option of making the Coordinate struct along with the convertCoordiante() function in ChessBoard public. However, this is not the smartest method so we opted for passing the check into ChessBoard instead.



Another challenge that occurred is whether to save setup for as long as the game is running or only for the next turn. We decided it is more reasonable to make it so that the setup is saved for every round. In order to achieve this, there needs to be a dedicated grid that saves the preset. It is also convenient to have a const grid that saves the default chess grid. Thus, for the sake of a clean design, we have a constant originGrid that stores the default chess placement, a setupGrid that can only be mutated in setup mode, and it is copied into grid every time the game starts. Grid is the only one that can be mutated mid game. A convenient function reset() is also implemented which copies originGrid into setupGrid. This originGrid -> setupGrid -> grid design ensures a clean hierarchy where an ongoing game cannot accidentally ruin the grid defined at setup, and changing setup does not cause forever loss of the default.
